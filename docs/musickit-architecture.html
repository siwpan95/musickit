一句话定位：musickit 是一个「真实采样 + 本地混音引擎」项目，由两个可独立运行的子系统组成。

  • 混音引擎（remix/ + music/ + burbidge_album/）：把素材池里的真实采样，按 phonk 风格 / 风格提示词 / 固定混音师签名链，渲染成 WAV/MP3 混音文件。纯命令行 / GUI，无网络。
  • 电台子系统（radio/）：纯 Flask 写的 24/7 网络电台。默认音源就是引擎的随机渲染输出——它把引擎当成一个无限素材发生器，套上 ICY/HLS/多码率/录音/控制面板，对外提供 HTTP 流 + 控制 API。

二者通过 文件系统 + 子进程 解耦：电台并不 import 引擎内部函数，而是 subprocess 调用 remix/tools/musickit_render_one.py，引擎崩了也不会带垮电台主进程（radio/radio/musickit_source.py:158）。

3.2 电台广播管线（含 musickit 源接入）

图 3 · 电台广播管线：一个广播者生产者，多路消费者（ICY 流 / 多码率 / HLS / 录音）
设计亮点（贴在项目代码注释里）：
  • D2 共享广播：N 个听众 = 1 次磁盘读（原来 N 次），Broadcaster.sub_count() 异常膨胀＝订阅泄漏（_push 的 finally 没跑到）。
  • 慢客户端背压：订阅队列满（maxsize=64）丢最旧块，听众跳秒不断流。
  • 快读客户端节流：_pace() 按码率限速，根治 ffmpeg/HLS 抽干节目的 29× 快读问题。
  • 引擎崩溃隔离：musickit 源是子进程，连续 5 次失败自动回退本地歌单（musickit_source.py:104）。

4. API 接口分析

项目实际暴露 两个独立的 HTTP 服务，且彼此端口不同。现有仓库里的 radio/radio/api_docs.py 只覆盖电台 8000 端口的一部分、且缺请求/响应 schema、缺示例、漏了若干真实路由。本交付物另生成两份完整 OpenAPI v3 规范：

① 电台控制 API

Flask · radio/run.py · 默认 :8000

~40 个路由：音频流（/stream、/stream/<bitrate>、/hls/<name>）、状态（/api/status、/api/health、/api/listeners、/api/stats/listeners）、播放控制（skip/play/stop/pause/shuffle/repeat/volume/rescan/record/musickit/request）、认证（/login、/api/auth/*）、文件（/api/upload、/api/files）、节目单、集成、文档（/api/openapi.json、/api/docs）。

→ radio-openapi.yaml

② 混音师流服务 API

http.server · remix/tools/mixer_stream.py · 默认 :8010

4 个路由：GET /api/channels（24 频道目录）、GET /api/stream/<slug>（无限流）、GET /api/track/<slug>?seed=&bars=（单曲下载）、GET /api/playlist/<slug>（m3u）。零依赖标准库实现。

→ mixer-stream-openapi.yaml

现有 api_docs.py 与实际代码的不一致（已修正于新规范）：
  • 文档表列了 POST /api/next，但 web.py 实际路由是 POST /api/skip——名字对不上。
  • api_docs API_DEFS 中 /api/files/<filename> 的 path 含一个零宽字符（U+200B），会导致 OpenAPI 路径参数解析异常；实际代码用的是 <path:filename>（uploads.py:176）。
  • 漏登记的真实路由：GET /api/musickit、GET /api/docs、GET /api/openapi.json、GET /api/public-url、GET /api/request/clear、POST /api/schedule/enable、GET /api/stats/listeners。
  • 现有 spec 所有 operation 的 responses 只有 200 成功，无 400/401/403/404、无请求体 schema、无示例——不可直接用于代码生成或客户端 SDK。

4.2 认证模型

密码以 SHA-256(salt:password) 落盘（.station_password，盐 16 字节 hex），首次 POST /login 即创建。未配置文件时本地/局域网信任模型：api_login_required 在 is_configured()==False 时视为已登录（否则新机器面板控制按钮会静默 401）。已配置后未登录的写操作返回 401 {"ok":false,"error":"请先登录"}。

7. 提示词利用率分析（⚠ 重点）

核心结论：提示词驱动混音「吃不全」提示词。生成器 music_prompt_generator.generate() 一次产出 12 个字段，但桥接器 music/prompt_driven_remix.py::prompt_to_mix_params() 实际只读取其中 5 个；真正改声音的只有 instruments 与 bpm 两个，label/subgenre/moods 仅用于从 3 个曲式模板里选 1 个，其余 7 个字段（scale / elements / scene / sentence / english / fusion / fusion_with）完全不进入音频。即提示词里相当比例的语义信息被静默丢弃。

7.1 字段级覆盖率矩阵

生成器字段含义是否驱动音频实际去向 / 映射备注
instruments[]乐器清单✅ 完全map_instrument → 37 类目 → 13 池 → 抽真实采样轨道（role_files）唯一决定「放什么声音」的字段；无样本乐器记入 gaps
bpm速度✅ 完全钳制到 [70,200] → run_remix(bpm=)决定整体速度
label风格名（如 Phonk）◐ 部分与 subgenre+moods 拼成小写文本，送入 choose_structure 命中 structure_moods.json 选曲式只影响曲式骨架，不动音色/编配
subgenre子流派名◐ 部分同上，仅进关键词 blob 选曲式同上
moods[]情绪词◐ 部分同上，进曲式关键词 blob同上
scale调式/音阶❌ 丢弃prompt_to_mix_params 不读取引擎无移调/调式 DSP，采样固定音高

统计口径：生成器 generate() 返回 12 字段（music_prompt_generator.py:239）；桥接器 prompt_to_mix_params 仅取 bpm / instruments / label / subgenre / moods（prompt_driven_remix.py:248/258/313）。其中 instruments + bpm 直接塑形音频，label/subgenre/moods 仅从 {ambient_ghost, classic_drop, loop_stack} 三选一，scale / elements / scene / sentence / english / fusion / fusion_with 共 7 字段从不进入音频管线。

7.2 为什么这值得强调

  • 提示词的「声学意图」大量落空：上游给出调式（scale）、氛围元素（elements）、场景（scene）时，期望听到对应的音乐色彩，但引擎对这些词没有任何响应——出来的曲子和没写这些词时一模一样。
  • 融合（fusion）名存实亡：generate(fusion=True) 会注入 fusion_with 第二类风格，但桥接器并不把融合对象当作额外乐器/约束，结果和单风格无差别。
  • 自然语言提示词（sentence）零利用率：这是最「像 AI 提示词」的字段，却只用于打印，完全没参与混音——对「提示词驱动」的叙事是个明显短板。
  • 信息不对称风险：--report 只记 label/bpm/structure/tracks/gaps，外部调用方无法从输出反推「哪些提示词被忽略」，容易误以为全部生效。

8. 结论

  • 架构清晰分层解耦：混音引擎（纯计算）+ 电台（纯服务）通过文件/子进程通信，任一半宕机不互相拖垮。
  • 性能设计扎实：共享广播缓冲 + 背压 + 节流，适合个人/小圈子电台（waitress 并发）。
  • 可复现性工程到位：每次渲染落 build_recipe + 引擎指纹，便于漂移归因。
    注（2026-11-02 修订）：原此处写「--release-safe 守住授权红线」，该表述已撤销 —— 素材均为公共领域，无需授权隔离；且该过滤曾被 B 变体绕过、并会砍掉 68.3% 素材，现已废弃。
  • API 文档是短板：既有 api_docs.py 路由名/字段不全、无示例，已用两份 OpenAPI v3 规范补齐（见同目录）。
  • 提示词利用率是第二大短板（重点）：生成器产出 12 字段，桥接器仅真正消费 instruments+bpm（另 3 字段只选曲式），scale/elements/scene/sentence/fusion 等 7 字段被静默丢弃。详见第 7 节覆盖率矩阵与强化建议——若要做到「提示词所写即所得」，需把被丢弃字段接入现有池/DSP（见 7.3）。
